## Design constraints (apply while framing, not as a post-hoc filter)

Read these before drafting. If you catch yourself *filtering* the root against these constraints after the fact, you have misread the task: the root should have been shaped to satisfy the constraints from the start. Stop, re-plan under the constraints, and generate correctly.

2. **A prompt for the tree, not a summary of the field.** Downstream branches will use the root's `description` as the anchor they push against. If a Wikipedia opener could stand in for the description, the root is under-scoped — sharpen the load-bearing tension until a downstream branch would know exactly which questions to push on. ## What to emit

A single JSON object — no prose, no code fences, just JSON — with these fields:

- `title` — one-line label for the root node. Phrase it as a research direction, not a question. ≤ 100 chars.
- `description` — 2–4 sentences. State the scope of the direction, what is interesting about it, and the load-bearing tensions / open questions branches will explore. Be concrete; avoid generic survey language.
- `next_action` — one sentence naming a concrete **entry point** for someone starting to explore this direction — which anchor paper to read first, which sub-area to prioritize, or which unresolved tension to interrogate. This scopes the tree's entry, it is not a research experiment (experiments live in child ideas produced by `expand`).
- `references` — array of 0–6 URLs / arxiv ids that anchor the direction. Constraint #1 above applies.

## Output

A single JSON object. No markdown, no fences, no commentary.
